## The Workflow Architecture
When you trigger a managed fine-tuning job on Vertex AI for Gemma, Google orchestrates the following automated pipeline:
```
[ GCS Bucket: data.jsonl ] ──> [ Vertex AI SFT Pipeline ] ──> [ Auto-allocated TPUs / GPUs ]
                                                                     │ (Trains Model & LoRA Adapters)
[ Vertex AI Endpoint ]    <── [ Vertex Model Registry ]   <── [ GCS Bucket: Saved Weights ]

```
 1. **Storage Isolation:** You store your data safely in your own Google Cloud Storage (GCS) bucket.
 2. **Compute Provisioning:** Vertex AI provisions a fleeting cluster of optimized accelerators (typically Google TPUs or NVIDIA L4/H100 GPUs depending on the model scale) dedicated entirely to your job.
 3. **Execution & Metric Tracking:** It runs the Supervised Fine-Tuning (SFT) loop, automatically hooking up to Vertex AI TensorBoard if you want to watch loss curves drop in real time.
 4. **Teardown & Register:** Once training is done, the compute cluster is destroyed instantly (you stop paying for hardware immediately). The fine-tuned weights/adapters are dumped into your GCS bucket and registered as an asset in the **Vertex AI Model Registry**.
## Technical Setup: Step-by-Step
### 1. Data Preparation (The JSONL Format)
Vertex AI expects your training data in a single or multi-line .jsonl file. For an instruction-tuned model like Gemma, you must format your rows to mimic a conversation structure:
```json
{"contents": [{"role": "user", "parts": [{"text": "Analyze this error: NullPointerException at line 42."}]}, {"role": "model", "parts": [{"text": "This occurs because the object reference at line 42 was initialized to null before a method call."}]}]}
{"contents": [{"role": "user", "parts": [{"text": "How do I clear the cache?"}]}, {"role": "model", "parts": [{"text": "Run 'systemctl restart cache-service' from your terminal root."}]}]}

```
Upload this file to a GCS bucket (e.g., gs://your-unique-bucket/tuning-data/train.jsonl).
### 2. The Python Implementation
You trigger the training using the vertexai Python SDK via the Supervised Fine Tuning (sft) module.
```python
import time
import vertexai
from vertexai.tuning import sft, SourceModel

# Initialize Vertex AI with your GCP project details
PROJECT_ID = "your-gcp-project-id"
REGION = "us-central1" # Or us-east4 / europe-west4 based on hardware availability
vertexai.init(project=PROJECT_ID, location=REGION)

# Trigger the managed fine-tuning pipeline
tuning_job = sft.train(
    # Point directly to the Gemma model identifier in Model Garden
    source_model=SourceModel(
        base_model="google/gemma3@gemma-3-27b-it" 
    ),
    # PEFT_ADAPTER tells Vertex to use LoRA (Parameter-Efficient Fine-Tuning)
    tuning_mode="PEFT_ADAPTER", 
    epochs=3,
    learning_rate_multiplier=1.0,
    
    # Define where data comes from and where the output adapters land
    train_dataset="gs://your-unique-bucket/tuning-data/train.jsonl",
    validation_dataset="gs://your-unique-bucket/tuning-data/validation.jsonl",
    output_uri="gs://your-unique-bucket/tuned-gemma-artifacts/"
)

# Optional: Monitor the job synchronously via polling
print(f"Tuning job started: {tuning_job.resource_name}")
while not tuning_job.has_ended:
    time.sleep(60)
    tuning_job.refresh()
    print("Training in progress...")

print("Tuning complete!")
print(f"Tuned Model Registry Name: {tuning_job.tuned_model_name}")

```

When scaling open-weights models like **Gemma 4 26B** (a Mixture-of-Experts model) using modern serving runtimes (such as vLLM or TensorRT-LLM) inside a Vertex AI shard/node, **QPS (Queries Per Second) is not a fixed number**.
Unlike a traditional web server database where 1 instance = 500 QPS, an LLM’s QPS is determined by three variables:
 1. **Input Prompt Length:** (How much context the GPU has to read at first).
 2. **Output Token Length:** (How many tokens the model has to generate sequentially).
 3. **The Target Latency Boundary:** (How long you are willing to let the user wait for their first token).
Evaluating what a single hardware shard running Gemma 4 26B can realistically handle highlights how scaling operates.
### The Baseline Numbers: QPS per Shard
Assuming a standard production payload—an average **input prompt of 500 tokens** and a **generated output response of 150 tokens**—using continuous batching and PagedAttention inside vLLM, a single instance can support the following ranges:
#### 1. The Cost-Optimized Shard (1x NVIDIA L4 GPU - Quantized FP4/INT4)
Because Gemma 4's Parallel Linear Experts (PLE) architecture isolates parameter activation, it maps heavily to modern FP4 optimizations.
 * **Total Token Throughput:** ~1,000 to 1,400 tokens per second combined across all active batches.
 * **Realistic Sustained QPS:** **~1.5 to 2.5 QPS**
 * *The Math:* If an average request consumes 150 generated tokens, the GPU handles roughly 2 stable requests concurrently per second before queues begin forming and latency spikes.
#### 2. The Enterprise Shard (1x NVIDIA A100 40GB/80GB - Native BF16)
The A100 features significantly wider memory bandwidth (HBM), which is the primary bottleneck when generating text.
 * **Total Token Throughput:** ~2,500 to 3,200 tokens per second.
 * **Realistic Sustained QPS:** **~4 to 6 QPS**
 * *The Math:* Stronger memory throughput lets the system pack higher continuous batch sizes, processing 4 to 6 requests simultaneously while maintaining a healthy Time-To-First-Token (TTFT).
### Scaling Bottlenecks: Concurrency vs. Latency
Understanding how the system reacts as traffic grows is critical. When multiple users hit a single shard simultaneously, vLLM groups them into a single parallel batch execution.
 * **Under Low Load (< 1 QPS):** The shard is underutilized. User latency is at its absolute lowest because the GPU instantly processes the prompt.
 * **Under Target Load (2 to 4 QPS on A100):** Continuous batching works perfectly. As one request finishes a token, a new request inserts itself into the execution cycle. Throughput spikes while user-perceived latency increases only minutely.
 * **Under Overload (> 7 QPS on a single A100):** The GPU runs out of physical KV Cache memory blocks to hold the conversation contexts. Requests get shoved into a waiting queue. **The QPS won't go higher; instead, your user latency increases exponentially.**
### How Vertex AI Scales Gemma 4 Automatically
Because one shard maxes out relatively early compared to legacy microservices, you utilize **Vertex AI’s Auto-Scaling Policy** to horizontal-scale your endpoints.
You configure your scaling rules based on target metrics rather than raw traffic metrics. Instead of telling Vertex AI to scale when CPU hits 80%, you monitor target resource indicators.
#### Recommended Auto-Scaling Configuration for Gemma 4 26B:
```json
{
  "autoscalingMetricSpecs": [{
    "metricName": "aiplatform.googleapis.com/prediction/online/accelerator_duty_cycle",
    "target": 80
  }],
  "minReplicaCount": 1,

}

```
 * **Accelerator Duty Cycle:** This tracks exactly how hard the GPU core is working. When your concurrent requests push the GPU's memory processing engine to a sustained 80% capacity, Vertex AI spins up a clean, duplicated shard (another L4 or A100 machine node).

## 2. Scaling Boundaries: When is Scaling Triggered?
In modern inference frameworks like vLLM (the standard backend for Model Garden open models), scaling is **not** dictated by a raw number of concurrent users, but by memory and compute thresholds.
### The Metrics That Drive Scaling
When setting up an auto-scaling policy on Vertex AI, you can configure it to listen to specialized framework metrics rather than just CPU usage:
 1. **accelerator_duty_cycle (GPU Utilization):** Triggers when the core math engines are continuously saturated.
 2. **vllm:num_requests_waiting (Queue Length):** Triggers when requests build up in the staging queue because the GPU is busy generating tokens for active users.
### Real-World Concurrency Scenario
Let’s look at a typical workflow scenario: **500 input tokens** (about a paragraph of context) and **150 output tokens** (a medium paragraph response).
 * **The Single-Node Ceiling:** A 2x A100 (80GB total) node running optimized continuous batching can efficiently process roughly **4 to 6 parallel calls per second (QPS)** before performance drops.
 * **The "Queue Wall" (Why Scaling is Needed):** LLMs generate tokens sequentially, one by one. If 15 users hit your API at the exact same millisecond, the framework will batch 6 or 7 of them together into an active execution loop. The remaining 8 users are paused in a waiting queue.
 * **The Trigger Point:** If your average queue depth (vllm:num_requests_waiting) stays above **5 requests** for a sustained 2-minute window, or your GPU duty cycle spikes past **80%**, Vertex AI’s auto-scaler recognizes a bottleneck and triggers a scale-up event.
## 3. Financial Impact When Scaled
When an auto-scale threshold is breached, Vertex AI handles scaling **horizontally**. It does not add a third GPU; it provisions a completely new, duplicate micro-service node instance (a2-highgpu-2g) alongside your original one.
```
                  ┌──> Shard 1 (2x A100) ──> [$6.74/hr]
[ Vertex Router ] ├──> Shard 2 (2x A100) ──> [$6.74/hr] (Provisioned during spike)
                  └──> Shard 3 (2x A100) ──> [$6.74/hr] (Provisioned during extreme peak)

```
The cost multiplies linearly based on how many clean instances are added to handle your peak traffic:
| Scale Level | Active Infrastructure | Total Hourly Burn | Equivalent Monthly Rate | Traffic Capacity |
|---|---|---|---|---|
| **Baseline (1 Node)** | 2x A100 (80GB) | **$6.74 / hr** | ~$4,852 / mo | ~4-6 QPS |
| **Scaled x2 (2 Nodes)** | 4x A100 (160GB) | **$13.48 / hr** | ~$9,705 / mo | ~8-12 QPS |
| **Scaled x4 (4 Nodes)** | 8x A100 (320GB) | **$26.96 / hr** | ~$19,411 / mo | ~16-24 QPS |
### The Scale-Down Lag
Vertex AI includes an intentional, built-in **cooldown period** (usually 5 to 10 minutes) after traffic drops before it terminates a scaled node. This prevents "flapping"—the expensive cycle of constantly killing and creating heavy VM instances if your traffic bounces up and down every few seconds. If a traffic spike lasts only 60 seconds, you will still pay for roughly 10 minutes of that scaled machine's runtime while it confirms the surge has passed.

### Reference 1: Multi-Argument Production Script
This production-style implementation uses command-line arguments to trigger the job—useful for automation engines, GitHub Actions pipelines, or Airflow orchestration scripts.
 * **Source Repository Layout:** Based on GoogleCloudPlatform/vertex-ai-samples/skills/vertex-tuning/scripts/tune_model.py
```python
"""Module for launching a managed Vertex AI model tuning job for Open Source Models."""
import argparse
import logging
import sys
import vertexai 
from vertexai.tuning import sft
from vertexai.tuning import SourceModel

logging.basicConfig(level=logging.INFO, format="%(asctime)s [%(levelname)s] %(message)s")

def launch_sft_job(
    project_id: str,
    location: str,
    bucket_uri: str,
    base_model_path: str,
    train_dataset_uri: str,
    validation_dataset_uri: str = None,
    output_uri: str = None,
    epochs: int = 3,
    learning_rate: float = 1.0,
    tuning_mode: str = "PEFT_ADAPTER",
) -> sft.SupervisedTuningJob:
    """Initializes the Vertex AI SDK and triggers the managed SFT framework."""
    
    logging.info("Initializing Vertex AI platform session...")
    vertexai.init(project=project_id, location=location, staging_bucket=bucket_uri)
    
    # Define the core model from Model Garden registry
    source_model_object = SourceModel(base_model_path)
    
    logging.info(f"Submitting Supervised Fine-Tuning job for target model: {base_model_path}")
    
    # Fire off the automated cloud training pipeline
    tuning_job = sft.train(
        source_model=source_model_object,
        train_dataset=train_dataset_uri,
        validation_dataset=validation_dataset_uri if validation_dataset_uri else None,
        epochs=epochs,
        learning_rate_multiplier=learning_rate, 
        tuning_mode=tuning_mode, # "PEFT_ADAPTER" maps to LoRA; "FULL" modifies all weights
        output_uri=output_uri if output_uri else None,
    )
    
    logging.info(f"Job creation acknowledged by GCP. Resource API string: {tuning_job.resource_name}")
    return tuning_job

if __name__ == "__main__":
    parser = argparse.ArgumentParser(description="CLI Tool for Vertex AI Open-Model Fine Tuning")
    parser.add_argument("--project", required=True, help="Your active GCP Project ID")
    parser.add_argument("--location", default="us-central1", help="Compute Engine hosting zone")
    parser.add_argument("--bucket", required=True, help="gs:// bucket path for staging configurations")
    parser.add_argument("--model", default="google/gemma4@gemma-4-26b-it", help="Model Garden target identifier")
    parser.add_argument("--train_uri", required=True, help="GCS URI path to training jsonl")
    parser.add_argument("--val_uri", default=None, help="Optional validation path")
    parser.add_argument("--output_uri", required=True, help="Target GCS destination for weights")
    
    args = parser.parse_args()
    
    job = launch_sft_job(
        project_id=args.project,
        location=args.location,
        bucket_uri=args.bucket,
        base_model_path=args.model,
        train_dataset_uri=args.train_uri,
        validation_dataset_uri=args.val_uri,
        output_uri=args.output_uri
    )

```
### Reference 2: The Interactive Notebook Workflow (With Asset Deployment)
This workflow handles formatting data locally, pushing it to Cloud Storage, executing the sft.train function, and extracting the final tuned endpoint.

```python
import time
import json
import vertexai
from vertexai.tuning import sft
from vertexai.preview import model_garden

# 1. Prepare your environment parameters
PROJECT_ID = "your-gcp-project-name"
LOCATION = "us-central1"
BUCKET_URI = "gs://your-mlops-bucket"
TRAIN_DATA_PATH = "gs://your-mlops-bucket/dataset/gemma_train.jsonl"

sft_job = sft.train(

while not sft_job.has_ended:

    sft_job.refresh()
    print(f" -> Current Cloud Pipeline Execution State: {sft_job.state}")

# Check final execution health state
if sft_job.state.name == "SUCCEEDED":
    print("\n[SUCCESS] Model training complete!")
    print(f"Registered Registry Model Path: {sft_job.tuned_model_name}")

    print("[INFO] Deploying output model directly to an active prediction node...")
    custom_model_instance = model_garden.CustomModel(sft_job.tuned_model_name)

        accept_eula=True

else:
    print(f"\n[FAILURE] Tuning failed with state termination code: {sft_job.state.name}")
```
